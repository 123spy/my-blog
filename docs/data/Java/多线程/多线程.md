很多人学 JUC 会出现两个问题：

1. **知识点背了一堆，但脑子里没有主线**
2. **代码会写一点，但不知道为什么这样写**

所以这份讲义不是单纯罗列 API，而是按下面三条线来组织：

- **主线一：并发为什么会出问题**
- **主线二：JUC 提供了哪些工具解决这些问题**
- **主线三：这些工具在工程里应该怎么用**

建议阅读方式：

- 第一遍：建立地图，知道每个工具解决什么问题
- 第二遍：重点啃 `JMM`、`volatile`、`CAS`、`AQS`、线程池
- 第三遍：把 `CompletableFuture`、线程池参数设计、并发容器和锁放到真实业务场景里理解

# 2. JUC 到底学什么

JUC 是 `java.util.concurrent` 的简称。

它不是只学“多线程怎么创建”，而是学一整套并发编程能力，包括：

- 线程基础
- 内存可见性与有序性
- 锁机制
- 原子操作
- 线程安全集合
- 阻塞队列
- 线程池
- 异步编排
- 并发工具类
- 并发设计思想

一句话概括：

> **JUC 研究的是：多个线程同时工作时，如何保证正确性、性能和可维护性。**

# 3. 线程与并发基础

## 3.1 进程与线程

### 进程
进程是操作系统进行资源分配的基本单位。

### 线程
线程是 CPU 调度的基本单位，一个进程可以有多个线程。

简单理解：

- 进程像一个工厂
- 线程像工厂里的工人
- 进程负责资源
- 线程负责执行任务

---

## 3.2 并发与并行

### 并发
同一时间段内，多个任务都在推进，但未必同一时刻真正同时执行。

### 并行
同一时刻多个任务真正同时执行。

在单核 CPU 上通常是“并发”；
在多核 CPU 上可以实现“并行”。

---

## 3.3 线程的创建方式

Java 常见线程创建方式：

### 方式一：继承 Thread

```java
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("thread running");
    }
}
~~~

### 方式二：实现 Runnable

```java
class MyRunnable implements Runnable {
    @Override
    public void run() {
        System.out.println("runnable running");
    }
}
```

### 方式三：实现 Callable + FutureTask

```java
Callable<Integer> callable = () -> {
    return 100;
};
FutureTask<Integer> futureTask = new FutureTask<>(callable);
new Thread(futureTask).start();
Integer result = futureTask.get();
```

### 方式四：线程池提交任务

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
pool.submit(() -> System.out.println("task running"));
pool.shutdown();
```

### 推荐理解

工程中最常用的是：

- `Runnable`
- `Callable`
- 线程池

**不建议在业务代码里频繁直接 new Thread()。**

------

## 3.4 线程状态

Java 线程有 6 种状态：

- `NEW`
- `RUNNABLE`
- `BLOCKED`
- `WAITING`
- `TIMED_WAITING`
- `TERMINATED`

### 简单解释

- `NEW`：刚创建还没启动
- `RUNNABLE`：可运行，可能正在运行，也可能等待 CPU
- `BLOCKED`：等待获取 monitor 锁
- `WAITING`：无限期等待
- `TIMED_WAITING`：限时等待
- `TERMINATED`：执行结束

------

## 3.5 wait / sleep / yield / join 区别

### sleep

- `Thread` 的静态方法
- 不释放锁
- 让当前线程休眠指定时间

### wait

- `Object` 的方法
- 必须在同步块中使用
- 会释放锁
- 通常用于线程通信

### yield

- 提示调度器当前线程愿意让出 CPU
- 不保证生效

### join

- 让当前线程等待目标线程执行完毕

# 4. 高并发为什么会出问题

多线程的核心问题通常集中在三点：

- 可见性
- 原子性
- 有序性

------

## 4.1 可见性

一个线程修改了共享变量，另一个线程什么时候能看到？

```java
boolean flag = false;
```

线程 A 修改：

```java
flag = true;
```

线程 B 可能一直看不到最新值。

这就是可见性问题。

------

## 4.2 原子性

一个操作看起来是一句代码，但底层可能不是一步完成。

```java
count++;
```

它通常包含三个步骤：

1. 读 count
2. count + 1
3. 写回 count

多个线程同时执行时就会丢失更新。

------

## 4.3 有序性

编译器和 CPU 可能为了优化对指令重排序。

单线程下没问题；
多线程下可能出问题。

经典例子：双重检查单例如果没有 `volatile`，可能因为重排序拿到“未完全初始化”的对象。

------

# 5. Java 内存模型 JMM

## 5.1 什么是 JMM

JMM（Java Memory Model）不是 JVM 内存结构图。

它描述的是：

> **在多线程环境下，共享变量如何被读取和写入，以及线程之间如何保证可见性、有序性。**

JMM 的核心目标是屏蔽不同硬件和编译器的差异，让 Java 并发行为具备统一语义。

------

## 5.2 happens-before

`happens-before` 是 JMM 中最重要的规则之一。

如果 A happens-before B，那么 A 的结果对 B 可见，并且 A 排序在 B 之前。

### 常见规则

#### 程序次序规则

同一个线程中，前面的操作 happens-before 后面的操作。

#### 监视器锁规则

对一个锁的解锁 happens-before 后续对这个锁的加锁。

#### volatile 规则

对一个 `volatile` 变量的写 happens-before 后续对这个变量的读。

#### 线程启动规则

`Thread.start()` 之前的操作，对新线程可见。

#### 线程终止规则

线程中的所有操作，对其他线程从 `join()` 成功返回后可见。

------

## 5.3 as-if-serial 与重排序

### as-if-serial

不管怎么优化，单线程执行结果不能变。

### 重排序

为了提高性能，编译器和 CPU 可以调整执行顺序。

在单线程中没问题；
多线程中如果没有同步手段，就会出现意想不到的问题。

------

# 6. synchronized 与锁升级理解

## 6.1 synchronized 用法

### 修饰实例方法

```java
public synchronized void add() {
    count++;
}
```

锁的是当前对象 `this`。

### 修饰静态方法

```java
public static synchronized void test() {
}
```

锁的是 `Class` 对象。

### 修饰代码块

```java
synchronized (lock) {
    count++;
}
```

锁的是括号里的对象。

------

## 6.2 对象锁和类锁

### 对象锁

不同对象，锁互不影响。

### 类锁

同一个类只有一把类锁，所有实例共享。

------

## 6.3 synchronized 的底层理解

`synchronized` 基于对象监视器（monitor）。

你可以把它理解成：

- 进入同步块：尝试抢锁
- 退出同步块：释放锁
- 抢不到：阻塞等待

JDK 早期很多人觉得 `synchronized` 重，但后续 JVM 对它做了大量优化，比如偏向锁、轻量级锁、自旋等。
所以今天不能简单说“`synchronized` 一定比 `Lock` 差”。

### synchronized 的优点

- 语法简单
- 自动释放锁
- JVM 层支持，稳定

### 缺点

- 功能相对单一
- 不能尝试获取锁
- 不能中断等待锁
- 不能绑定多个条件队列

------

# 7. volatile 关键字

## 7.1 volatile 能解决什么

`volatile` 的两个主要作用：

- 保证可见性
- 禁止特定重排序

### 示例

```java
class Demo {
    volatile boolean flag = false;

    public void write() {
        flag = true;
    }

    public void read() {
        while (!flag) {
        }
        System.out.println("detected");
    }
}
```

没有 `volatile` 时，读线程可能一直看不到最新值。

------

## 7.2 volatile 不能解决什么

`volatile` **不能保证复合操作的原子性**。

比如：

```java
volatile int count = 0;
count++;
```

这仍然不是线程安全的。

------

## 7.3 典型场景

### 状态标记

```java
volatile boolean shutdown = false;
```

### 双重检查单例

```java
class Singleton {
    private static volatile Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

这里必须用 `volatile`，否则可能发生指令重排序。

------

# 8. CAS 与原子类

## 8.1 什么是 CAS

CAS：Compare And Swap / Compare And Set

核心思想：

> 比较内存中的值是否是预期值，如果是，就更新；如果不是，就失败重试。

伪代码：

```java
if (value == expected) {
    value = newValue;
}
```

CAS 是很多无锁算法的基础。

------

## 8.2 ABA 问题

CAS 只看“值有没有变化”，不看“变化过程”。

比如：

- 初始值 A
- 线程 1 读取到 A
- 线程 2 把 A 改成 B
- 线程 2 又把 B 改回 A
- 线程 1 再 CAS，会以为没变

这就是 ABA 问题。

### 解决思路

引入版本号：

- `AtomicStampedReference`
- `AtomicMarkableReference`

------

## 8.3 常见原子类

### 基本类型

- `AtomicInteger`
- `AtomicLong`
- `AtomicBoolean`

### 数组

- `AtomicIntegerArray`
- `AtomicLongArray`

### 引用

- `AtomicReference`
- `AtomicStampedReference`

### 字段更新器

- `AtomicIntegerFieldUpdater`
- `AtomicLongFieldUpdater`
- `AtomicReferenceFieldUpdater`

### 累加器

- `LongAdder`
- `LongAccumulator`

### 为什么 LongAdder 高并发更好

`AtomicLong` 在高并发下大量竞争一个变量；
`LongAdder` 通过分段累加减少冲突。

代价是：

- 求和时不是绝对“单点瞬时值”
- 占用更多空间

------

# 9. Lock 接口与 ReentrantLock

## 9.1 为什么还需要 Lock

`synchronized` 已经能加锁了，为什么还要 `Lock`？

因为 `Lock` 提供了更灵活的能力：

- 可中断获取锁
- 可尝试获取锁
- 可超时获取锁
- 可绑定多个条件队列
- 更灵活的公平策略

------

## 9.2 ReentrantLock 的特性

### 可重入

同一个线程可以重复获取同一把锁。

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // business
} finally {
    lock.unlock();
}
```

### 为什么一定要 finally 释放

因为 `Lock` 不会像 `synchronized` 那样自动释放，
必须手动释放。

------

## 9.3 公平锁与非公平锁

### 公平锁

按等待顺序获取锁。

### 非公平锁

允许插队，吞吐量通常更高。

```java
Lock fairLock = new ReentrantLock(true);
Lock unfairLock = new ReentrantLock(false);
```

### 选择建议

- 对吞吐量要求高：一般非公平
- 对等待顺序敏感：考虑公平锁

------

## 9.4 Condition 的使用

`Condition` 类似于 `wait/notify` 的增强版。

一个锁可以绑定多个条件队列。

```java
Lock lock = new ReentrantLock();
Condition condition = lock.newCondition();

lock.lock();
try {
    condition.await();
    condition.signal();
} finally {
    lock.unlock();
}
```

优势：

- 更精细的线程唤醒
- 比 `notifyAll` 更可控

------

# 10. AQS：很多并发工具的底座

## 10.1 AQS 是什么

AQS = `AbstractQueuedSynchronizer`

它是 Java 并发包里非常核心的一个同步框架。

很多并发工具底层都基于它实现，比如：

- `ReentrantLock`
- `CountDownLatch`
- `Semaphore`
- `ReentrantReadWriteLock`

------

## 10.2 独占与共享

AQS 支持两种获取资源模式：

### 独占模式

同一时刻只有一个线程获取资源。

例子：

- `ReentrantLock`

### 共享模式

同一时刻多个线程可以共享资源。

例子：

- `Semaphore`
- `CountDownLatch`
- 读锁

------

## 10.3 为什么 AQS 很重要

因为它统一解决了下面这些问题：

- 用一个 `state` 表示同步状态
- 获取失败的线程如何入队等待
- 如何唤醒后继节点
- 如何处理中断和超时

你不一定要手写 AQS，
但你必须知道：

> **很多 JUC 工具并不是“各自独立的一堆 API”，而是建立在同一套同步框架上的。**

理解了 AQS，很多工具你就能串起来看。

------

# 11. 线程间通信与生产者消费者

## 11.1 经典模型

最经典的问题：

- 生产者生产数据
- 消费者消费数据
- 缓冲区满了，生产者等待
- 缓冲区空了，消费者等待

------

## 11.2 if 和 while 的区别

在等待条件时必须优先考虑 `while`，不要轻易写 `if`。

### 错误示例

```java
if (number == 0) {
    condition.await();
}
```

### 正确示例

```java
while (number == 0) {
    condition.await();
}
```

### 为什么？

因为可能出现：

- 虚假唤醒
- 被唤醒后条件仍不满足

所以要重新检查条件。

------

## 11.3 notify 和 notifyAll

### notify

随机唤醒一个等待线程。

### notifyAll

唤醒所有等待线程。

### 实战建议

如果多个线程等待同一条件，且线程角色复杂，
`notifyAll` 往往更安全；
如果使用 `Condition`，通常可以按条件队列精准唤醒。

------

# 12. 常用并发工具类

## 12.1 CountDownLatch

倒计数器。

适用场景：

- 主线程等待多个子任务完成后再继续

```java
CountDownLatch latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        System.out.println(Thread.currentThread().getName() + " finish");
        latch.countDown();
    }).start();
}

latch.await();
System.out.println("all finish");
```

特点：

- 计数只能减，不能重置
- 一次性使用更常见

------

## 12.2 CyclicBarrier

循环栅栏。

适用场景：

- 一组线程彼此等待，凑齐后一起继续

```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> {
    System.out.println("all ready");
});
```

### CountDownLatch 和 CyclicBarrier 区别

- `CountDownLatch`：一个线程等其他线程
- `CyclicBarrier`：一组线程互相等待

------

## 12.3 Semaphore

信号量。

适用场景：

- 限流
- 限制并发访问数量

```java
Semaphore semaphore = new Semaphore(3);

semaphore.acquire();
try {
    // business
} finally {
    semaphore.release();
}
```

------

## 12.4 Exchanger

两个线程交换数据。

适用场景较少，但在成对线程交换结果时很方便。

------

## 12.5 Phaser

比 `CountDownLatch` / `CyclicBarrier` 更灵活的阶段控制器。

适合多阶段协作任务。

------

# 13. 读写锁与 StampedLock

## 13.1 ReadWriteLock

读多写少场景常用。

- 读锁共享
- 写锁独占

```java
ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();

rwLock.readLock().lock();
try {
    // read
} finally {
    rwLock.readLock().unlock();
}
```

### 适用场景

- 缓存
- 配置读取
- 读远多于写的数据结构

### 注意

写锁会阻塞读写；
读锁并发高时能提升吞吐量。

------

## 13.2 StampedLock

`StampedLock` 是 JDK 8 引入的更现代的锁工具。

特点：

- 写锁
- 悲观读锁
- 乐观读

### 乐观读

先不真正加读锁，读取后检查期间是否有写发生。

优点：

- 读多写少场景性能可能更好

注意：

- 不是可重入锁
- 使用复杂度更高
- 不适合作为入门第一选择

# 14. 线程安全集合与并发容器

## 14.1 为什么普通集合不安全

以 `ArrayList` 为例，多线程同时 add 可能出现：

- 数据覆盖
- 下标越界
- 状态不一致

### 错误示例

```java
List<String> list = new ArrayList<>();
for (int i = 0; i < 30; i++) {
    new Thread(() -> {
        list.add(UUID.randomUUID().toString());
        System.out.println(list);
    }).start();
}
```

------

## 14.2 CopyOnWriteArrayList

写时复制思想：

- 写操作时复制底层数组
- 修改副本
- 再替换引用

优点：

- 读不加锁或读开销很低
- 适合读多写少

缺点：

- 写开销大
- 占内存
- 不适合频繁写

适用场景：

- 黑名单配置
- 白名单配置
- 监听器列表
- 读多写少的快照式数据

------

## 14.3 ConcurrentHashMap

这是并发集合中的重点。

### JDK 7 思路

分段锁 `Segment`

### JDK 8 思路

- 数组 + 链表 + 红黑树
- CAS + synchronized
- 降低锁粒度

### 特点

- 高并发性能较好
- 支持安全并发访问
- 不允许 key/value 为 null

### 为什么不允许 null

因为在并发环境下，`get(key) == null` 无法区分：

- key 不存在
- value 本身为 null

## 14.4 BlockingQueue 家族

`BlockingQueue` 是线程池、生产消费模型的重要基础。

常见实现：

- `ArrayBlockingQueue`
- `LinkedBlockingQueue`
- `SynchronousQueue`
- `PriorityBlockingQueue`
- `DelayQueue`
- `LinkedTransferQueue`

# 15. 阻塞队列详解

## 15.1 四组 API

阻塞队列常见操作可以分四类：

| 类型 | 抛异常  | 返回特殊值 | 阻塞 | 超时        |
| ---- | ------- | ---------- | ---- | ----------- |
| 插入 | add     | offer      | put  | offer(time) |
| 移除 | remove  | poll       | take | poll(time)  |
| 检查 | element | peek       | -    | -           |

### 理解重点

不同场景要选不同风格的 API：

- 强约束：抛异常
- 容忍失败：返回布尔或 null
- 流控：阻塞
- 需要边界控制：超时

------

## 15.2 常见实现

### ArrayBlockingQueue

- 有界
- 基于数组
- 需要提前指定容量

### LinkedBlockingQueue

- 可选有界/默认近似无界
- 基于链表
- 生产消费较常见

### SynchronousQueue

- 不存元素
- 一个插入必须等一个取走

### PriorityBlockingQueue

- 按优先级出队
- 无界

### DelayQueue

- 延迟队列
- 只有到期元素才能取出

------

## 15.3 适用场景

### ArrayBlockingQueue

需要明确容量上限的场景。

### LinkedBlockingQueue

一般生产消费模型。

### SynchronousQueue

直接移交任务，常见于缓存线程池模型。

### DelayQueue

超时任务、延迟消息。

------

# 16. 线程池：JUC 中最重要的工程能力

## 16.1 为什么要用线程池

频繁创建和销毁线程成本高。

线程池的好处：

- 降低线程创建开销
- 复用线程
- 控制并发数量
- 统一管理任务
- 支持队列缓冲
- 支持拒绝策略和监控扩展

一句话：

> **线程池的本质，是一种受控的任务执行框架。**

------

## 16.2 七大参数

`ThreadPoolExecutor` 的核心构造参数：

```java
public ThreadPoolExecutor(
    int corePoolSize,
    int maximumPoolSize,
    long keepAliveTime,
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,
    ThreadFactory threadFactory,
    RejectedExecutionHandler handler)
```

### 1. corePoolSize

核心线程数。

### 2. maximumPoolSize

最大线程数。

### 3. keepAliveTime

非核心线程空闲存活时间。

### 4. unit

时间单位。

### 5. workQueue

任务队列。

### 6. threadFactory

线程工厂。

### 7. handler

拒绝策略。

------

## 16.3 工作流程

线程池接收任务时，大致流程：

1. 如果运行线程数 < `corePoolSize`，直接创建核心线程执行
2. 否则尝试入队
3. 如果队列满了，且线程数 < `maximumPoolSize`，创建非核心线程执行
4. 如果队列也满，线程数也到上限，触发拒绝策略

这个流程必须背熟。

------

## 16.4 拒绝策略

JDK 提供 4 种常见拒绝策略：

### AbortPolicy

默认策略，直接抛异常。

### CallerRunsPolicy

由提交任务的线程自己执行任务。

### DiscardPolicy

直接丢弃任务，不报错。

### DiscardOldestPolicy

丢弃队列中最旧的任务，再尝试提交当前任务。

### 实战建议

线上一般不建议直接静默丢弃，除非业务可接受。

------

## 16.5 Executors 为什么不推荐滥用

很多入门资料喜欢这样写：

```java
Executors.newFixedThreadPool(5);
Executors.newCachedThreadPool();
Executors.newSingleThreadExecutor();
```

它们能用，但工程上不建议无脑使用。

### 原因一：参数不可控

你看不到底层关键参数，容易出问题。

### 原因二：可能带来资源风险

例如：

- 某些默认队列过大
- 某些最大线程数可能非常大

结果可能导致：

- 内存堆积
- 请求堆积
- 系统雪崩

### 工程建议

优先显式使用 `ThreadPoolExecutor` 自定义参数。

------

## 16.6 如何合理设置线程池参数

这是面试和工程都非常重要的一点。

### CPU 密集型任务

特点：

- 计算多
- 阻塞少

建议线程数接近 CPU 核数：

```text
CPU 核数 或 CPU 核数 + 1
```

### IO 密集型任务

特点：

- 等待多
- CPU 不是瓶颈

线程数通常可以比 CPU 核数大很多。

经验公式常见写法：

```text
线程数 = CPU核数 * (1 + 等待时间 / 计算时间)
```

### 核心不是公式，而是：

- 任务是 CPU 密集还是 IO 密集
- 是否允许排队
- 队列能承受多少堆积
- 超载时怎么处理
- 是否需要隔离不同业务池

### 最佳实践

不同业务不要共用一个大线程池。

比如分开：

- RPC 调用池
- MQ 消费池
- 定时任务池
- 异步日志池

这样更容易隔离故障。

------

# 17. Future、Callable、FutureTask

### Callable

有返回值，可以抛异常。

### Future

表示异步结果，可以：

- 判断是否完成
- 获取结果
- 取消任务

### FutureTask

同时实现了 `Runnable` 和 `Future`，是桥梁类。

### 示例

```java
Callable<Integer> callable = () -> 200;
FutureTask<Integer> task = new FutureTask<>(callable);
new Thread(task).start();
Integer result = task.get();
```

### Future 的问题

`get()` 往往是阻塞的，不适合复杂异步编排。

所以在现代 Java 中，更多会用 `CompletableFuture`。

------

# 18. CompletableFuture：异步编排核心

## 18.1 基础使用

### runAsync

无返回值。

```java
CompletableFuture<Void> future = CompletableFuture.runAsync(() -> {
    System.out.println("run async");
});
```

### supplyAsync

有返回值。

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    return 10;
});
```

------

## 18.2 串行组合

### thenApply

拿到上一步结果，做转换。

```java
CompletableFuture<Integer> future = CompletableFuture
        .supplyAsync(() -> 10)
        .thenApply(x -> x * 2);
```

### thenAccept

消费结果，无返回值。

```java
CompletableFuture
        .supplyAsync(() -> 10)
        .thenAccept(System.out::println);
```

### thenRun

不关心前面结果，只在后续执行一个动作。

```java
CompletableFuture
        .supplyAsync(() -> 10)
        .thenRun(() -> System.out.println("done"));
```

### thenCompose

把两个异步任务串起来。

```java
CompletableFuture<Integer> future = CompletableFuture
        .supplyAsync(() -> 10)
        .thenCompose(x -> CompletableFuture.supplyAsync(() -> x + 20));
```

------

## 18.3 并行组合

### thenCombine

两个任务都完成后合并结果。

```java
CompletableFuture<Integer> f1 = CompletableFuture.supplyAsync(() -> 10);
CompletableFuture<Integer> f2 = CompletableFuture.supplyAsync(() -> 20);

CompletableFuture<Integer> result = f1.thenCombine(f2, Integer::sum);
```

### allOf

等待所有任务完成。

```java
CompletableFuture<Void> all = CompletableFuture.allOf(f1, f2);
```

### anyOf

任意一个完成即可继续。

```java
CompletableFuture<Object> any = CompletableFuture.anyOf(f1, f2);
```

------

## 18.4 异常处理

### exceptionally

出现异常时给默认值。

```java
CompletableFuture<Integer> future = CompletableFuture
        .supplyAsync(() -> 10 / 0)
        .exceptionally(ex -> -1);
```

### handle

无论成功失败都能处理。

```java
CompletableFuture<Integer> future = CompletableFuture
        .supplyAsync(() -> 10 / 0)
        .handle((res, ex) -> {
            if (ex != null) {
                return -1;
            }
            return res;
        });
```

### whenComplete

做结果回调，但不改变结果。

```java
CompletableFuture<Integer> future = CompletableFuture
        .supplyAsync(() -> 10)
        .whenComplete((res, ex) -> {
            System.out.println("result = " + res);
        });
```

------

## 18.5 实战建议

### 1. 默认线程池不要无脑用

`CompletableFuture` 默认异步执行常会用公共线程池。
真实业务里建议根据场景传入自定义线程池。

```java
ExecutorService pool = new ThreadPoolExecutor(
        4, 8, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(100),
        Executors.defaultThreadFactory(),
        new ThreadPoolExecutor.AbortPolicy()
);

CompletableFuture.supplyAsync(() -> {
    return "hello";
}, pool);
```

### 2. 区分同步回调和异步回调

- `thenApply`：可能由当前线程继续执行
- `thenApplyAsync`：异步执行，可指定线程池

### 3. 异步链不要失控

不要把业务逻辑堆成很长一条链而没有边界管理。

### 4. 注意异常传播

很多人只写成功链，不处理异常链，线上很容易埋雷。

### 5. 注意超时

真实业务的异步编排通常要考虑：

- 单任务超时
- 总链路超时
- 降级与兜底

------

# 19. ForkJoin 框架

ForkJoin 适合：

> **把一个大任务拆成多个小任务并行计算，再合并结果。**

核心思想：

- `fork`：拆分任务
- `join`：合并结果

典型例子：

- 大数组求和
- 分治计算
- 并行递归任务

### 示例思路

如果区间很小，直接算；
如果区间很大，拆成左右两半递归。

### 工作窃取

ForkJoinPool 支持工作窃取：
空闲线程会去“偷”其他线程队列里的任务，提高吞吐量。

### 注意

它适合可拆分、CPU 密集型任务；
不适合大量阻塞 IO 场景。

# 20. 死锁、活锁、饥饿

## 死锁

两个或多个线程互相等待对方释放资源，导致永远卡住。

### 死锁四个必要条件

- 互斥
- 占有且等待
- 不可剥夺
- 循环等待

### 经典示例

```java
Object a = new Object();
Object b = new Object();

new Thread(() -> {
    synchronized (a) {
        synchronized (b) {
        }
    }
}).start();

new Thread(() -> {
    synchronized (b) {
        synchronized (a) {
        }
    }
}).start();
```

### 避免思路

- 固定加锁顺序
- 尽量减少锁嵌套
- 使用 `tryLock`
- 缩小锁粒度

------

## 活锁

线程没有阻塞，但一直互相让步，导致任务始终无法推进。

------

## 饥饿

某些线程长期拿不到资源。

常见原因：

- 锁不公平
- 优先级不合理
- 资源一直被热点线程占用

------

# 21. 并发编程中的常见误区

## 误区 1：给变量加了 volatile 就线程安全了

错。
`volatile` 只能保证可见性和一定的有序性，不能保证复合操作原子性。

------

## 误区 2：synchronized 一定很慢

过时认知。
现代 JVM 对 `synchronized` 做了很多优化。

------

## 误区 3：线程越多越快

错。
线程过多会导致：

- 上下文切换开销增加
- 内存占用增加
- 调度竞争加剧

------

## 误区 4：线程池只要能跑就行

错。
线程池参数不合理是线上事故高发区。

------

## 误区 5：CopyOnWriteArrayList 是通用线程安全 List

错。
它只适合读多写少。

------

## 误区 6：ConcurrentHashMap 就没有并发风险了

不对。
单个操作线程安全，不等于复合逻辑线程安全。

比如：

```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

这仍然可能有并发问题。

更合适的是：

```java
map.putIfAbsent(key, value);
```

------

## 误区 7：CompletableFuture 写成链就一定优雅

不一定。
过长、无监控、无异常兜底的异步链，非常难维护。

------

# 22. 面试高频问题整理

## 1. synchronized 和 Lock 的区别

### synchronized

- JVM 层面
- 自动释放锁
- 用法简单

### Lock

- JDK 层面
- 需手动释放
- 更灵活，可中断、可超时、可绑定多个条件

------

## 2. volatile 的作用是什么

- 保证可见性
- 禁止特定重排序
- 不保证原子性

------

## 3. CAS 有什么问题

- ABA 问题
- 自旋时间长开销大
- 只能保证单个共享变量的原子更新

------

## 4. AQS 是什么

AQS 是一个同步器框架，很多锁和同步工具都基于它实现。

------

## 5. ReentrantLock 为什么叫可重入

同一个线程可以重复获取同一把锁而不会死锁。

------

## 6. CountDownLatch 和 CyclicBarrier 区别

- `CountDownLatch`：一个等多个
- `CyclicBarrier`：多个互等
- `CountDownLatch` 更偏一次性
- `CyclicBarrier` 可以重复利用

------

## 7. ConcurrentHashMap 为什么线程安全

JDK 8 中通过数组、链表、红黑树、CAS 与同步控制配合实现高效并发。

------

## 8. 线程池参数怎么配

- 先判断 CPU 密集还是 IO 密集
- 再看队列容量、最大线程数、拒绝策略
- 最后结合压测与监控调整

------

## 9. 为什么不建议直接用 Executors 创建线程池

因为默认参数可能导致资源不可控，带来堆积或 OOM 风险。

------

## 10. CompletableFuture 和 Future 区别

- `Future` 更偏“拿结果”
- `CompletableFuture` 更偏“异步任务编排”

------

# 附录 B：一个建议背熟的线程池模板

```java
import java.util.concurrent.*;

public class ThreadPoolTemplate {
    public static void main(String[] args) {
        ExecutorService pool = new ThreadPoolExecutor(
                4,
                8,
                60L,
                TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(100),
                new ThreadFactory() {
                    private int count = 1;
                    @Override
                    public Thread newThread(Runnable r) {
                        return new Thread(r, "biz-pool-" + count++);
                    }
                },
                new ThreadPoolExecutor.CallerRunsPolicy()
        );

        try {
            for (int i = 0; i < 20; i++) {
                int taskId = i;
                pool.submit(() -> {
                    System.out.println(Thread.currentThread().getName() + " execute task " + taskId);
                });
            }
        } finally {
            pool.shutdown();
        }
    }
}
```

### 这个模板为什么比 Executors 更适合练习

因为你能明确感知：

- 核心线程数
- 最大线程数
- 队列容量
- 拒绝策略
- 线程命名

工程里这些都很关键。

# 附录 C：一个 CompletableFuture 聚合示例

```java
import java.util.concurrent.*;

public class CompletableFutureDemo {

    public static void main(String[] args) {
        ExecutorService pool = new ThreadPoolExecutor(
                4, 8, 60, TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(100),
                Executors.defaultThreadFactory(),
                new ThreadPoolExecutor.AbortPolicy()
        );

        try {
            CompletableFuture<String> userFuture = CompletableFuture.supplyAsync(() -> {
                sleep(200);
                return "user-info";
            }, pool);

            CompletableFuture<String> orderFuture = CompletableFuture.supplyAsync(() -> {
                sleep(300);
                return "order-info";
            }, pool);

            CompletableFuture<String> couponFuture = CompletableFuture.supplyAsync(() -> {
                sleep(100);
                return "coupon-info";
            }, pool);

            CompletableFuture<String> resultFuture = userFuture.thenCombine(orderFuture,
                    (u, o) -> u + " | " + o)
                    .thenCombine(couponFuture, (uo, c) -> uo + " | " + c)
                    .exceptionally(ex -> "fallback-result");

            System.out.println(resultFuture.join());
        } finally {
            pool.shutdown();
        }
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

# 结语

学习 JUC 最怕两种状态：

- 只背概念，不写代码
- 只抄代码，不懂原理

真正有效的方法是：

1. 先建立整体地图
2. 再补关键原理
3. 最后结合工程场景练习

你不需要一上来就把所有底层源码都看懂，
但你至少要逐步做到：

- 知道问题是什么
- 知道工具解决什么
- 知道什么时候该用、什么时候不该用

当你把下面这些点真正串起来时，JUC 就算学进去了：

- JMM
- synchronized / Lock
- volatile
- CAS / AQS
- 并发容器
- BlockingQueue
- ThreadPoolExecutor
- CompletableFuture

学到这里，你不只是“会一点多线程”，而是开始具备并发编程能力了。
