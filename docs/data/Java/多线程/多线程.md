# 第一课：为什么会有 JUC？多线程到底会出什么问题？

学 JUC 之前，先要弄明白一个问题：

**Java 为什么要专门搞一套并发工具包？**

答案很简单：

**因为多线程一旦同时操作共享资源，就很容易出问题。**

JUC 的存在，就是为了更好地解决这些问题。

------

# 一、先理解什么是“并发”

你可以把程序想成一家餐厅。

- 一个厨师做一道菜，这是单线程
- 多个厨师同时做菜，这是多线程
- 多个厨师如果各做各的，通常没问题
- 但如果他们同时抢同一个锅、同一把刀、同一份食材，就会乱

这个“同一个锅、刀、食材”，在程序里就叫：

**共享资源**

比如：

- 一个变量
- 一个集合
- 一个对象里的字段
- 一个文件
- 一个数据库记录

只要多个线程同时操作这些共享资源，就可能出现线程安全问题。

------

# 二、多线程最典型的问题：数据错乱

先看一个最经典的例子。

假设有一个变量 `count = 0`，两个线程同时给它加 1。

你可能以为最后一定是 2。

但实际不一定。

来看代码：

```java
public class Demo1 {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 10000; i++) {
                count++;
            }
        });

        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 10000; i++) {
                count++;
            }
        });

        t1.start();
        t2.start();

        t1.join();
        t2.join();

        System.out.println("最终结果: " + count);
    }
}
```

你直觉上会觉得输出应该是：

```java
20000
```

但很多时候结果会小于 `20000`。

为什么？

因为：

**`count++` 不是一个原子操作。**

它实际上分成 3 步：

1. 读取 `count`
2. `count + 1`
3. 写回 `count`

假设两个线程同时执行：

- 线程 A 读到 `count = 5`
- 线程 B 也读到 `count = 5`
- A 加 1 变成 6，写回
- B 也加 1 变成 6，写回

结果本来应该加两次，最后却只加了一次。

这就叫：

**竞态条件**
（多个线程竞争执行顺序，导致结果不确定）

------

# 三、为什么单线程没事，多线程就出问题

单线程时，代码是一行一行顺着执行的。

比如：

```java
count++;
count++;
```

结果很稳定。

但多线程时，CPU 会在多个线程之间来回切换执行。
你看到的是两段代码同时跑，实际上底层可能是这样交错的：

- 线程 A 执行一半
- 切到线程 B
- 线程 B 执行一半
- 再切回线程 A

这种交错执行就会导致：

- 数据丢失
- 顺序混乱
- 结果不一致

所以并发问题的根源是：

**多个线程共享数据 + 执行顺序不可控**

------

# 四、线程安全问题的三个核心概念

学 JUC，最重要的三个词你现在就要记住：

## 1. 原子性

一个操作要么全部做完，要么完全不做，中间不能被打断。

比如：

```java
count++;
```

它不是原子的。

而像某些加锁后的操作，或者原子类操作，才具备原子性。

------

## 2. 可见性

一个线程修改了共享变量，另一个线程能不能立刻看到这个最新值。

比如：

- 线程 A 把 `flag` 改成 `true`
- 线程 B 一直在读 `flag`

如果 B 看不到 A 改后的值，就会出问题。

这就是可见性问题。

------

## 3. 有序性

程序执行时，代码顺序不一定完全按你写的顺序来。

编译器、CPU 为了优化，可能会做**指令重排**。

单线程下通常没问题，但多线程下可能出事。

------

# 五、先理解一个经典可见性问题

看代码：

```java
public class Demo2 {
    static boolean flag = false;

    public static void main(String[] args) {
        new Thread(() -> {
            while (!flag) {
            }
            System.out.println("线程结束了");
        }).start();

        new Thread(() -> {
            flag = true;
            System.out.println("flag 已修改为 true");
        }).start();
    }
}
```

你以为第二个线程把 `flag = true` 后，第一个线程就会停下。

但在某些情况下，第一个线程可能一直不结束。

原因是：

第一个线程可能一直读的是自己的工作内存里的旧值，而不是主内存里的新值。

这就是可见性问题。

后面学 `volatile`，就是专门处理这类问题。

------

# 六、除了数据错乱，还会有哪些问题

多线程不是只会“结果少几次”这么简单，它还会引出很多问题。

## 1. 线程安全问题

多个线程改同一份数据，结果不对。

比如：

- 余额计算错误
- 库存扣减错误
- 计数器不准

------

## 2. 活跃性问题

程序不是算错了，而是“卡住了”。

### 死锁

线程 A 等线程 B 的锁，线程 B 又等线程 A 的锁，谁都不让谁。

### 饥饿

某些线程一直抢不到资源。

### 活锁

线程都在让来让去，但谁都完成不了工作。

------

## 3. 性能问题

你以为多线程更快，但实际上可能更慢。

因为：

- 线程创建有成本
- 线程切换有成本
- 加锁有成本
- 竞争严重时效率下降

所以并发编程不是“线程越多越好”。

------

# 七、那 JUC 到底是来解决什么的

JUC 就是 Java 官方提供的一套并发工具。

它主要帮你解决这几类问题：

## 1. 如何安全操作共享数据

比如：

- `AtomicInteger`
- `ConcurrentHashMap`
- 各种锁

------

## 2. 如何更灵活地控制线程

比如：

- `ReentrantLock`
- `Condition`

------

## 3. 如何让多个线程协作

比如：

- `CountDownLatch`
- `CyclicBarrier`
- `Semaphore`

------

## 4. 如何高效管理线程

比如：

- `ThreadPoolExecutor`
- `Future`
- `Callable`

------

# 八、为什么不用最原始的 Thread 就够了

早期你当然可以只用：

- `Thread`
- `synchronized`
- `wait/notify`

但问题是：

这些东西太底层，写复杂一点就容易乱。

比如你要实现：

如果全靠原始方式手写，会很麻烦，也很容易写错。

所以 JUC 本质上就是：

**把常见并发问题封装成现成工具，减少你自己造轮子。**

这一课很关键。

# 一、先想一个问题：线程为什么会“看不见”彼此修改的数据？

先看这个代码：

```java
public class Demo {
    static boolean flag = false;

    public static void main(String[] args) {
        new Thread(() -> {
            while (!flag) {
            }
            System.out.println("结束循环");
        }).start();

        new Thread(() -> {
            flag = true;
            System.out.println("flag 改成 true");
        }).start();
    }
}
```

你直觉上会觉得：

- 第二个线程把 `flag = true`
- 第一个线程就会退出循环

但实际不一定。

为什么？

因为在线程世界里，**每个线程不一定每次都直接从主内存读取数据**。

它可能会：

- 先把共享变量从主内存拷贝到自己的“工作区域”
- 后面反复使用自己的副本
- 这样别的线程改了主内存，它未必马上知道

这就是并发问题出现的重要根源。

------

# 二、什么是 Java 内存模型（JMM）

你先别把它想得太复杂。

你可以把 JMM 理解成：

**Java 规定的，多线程之间变量如何读、如何写、什么时候对别的线程可见的一套规则。**

它不是一个真实存在的“内存区域”，更像一套规范。

你可以先用这个简化模型理解：

## 1. 主内存

共享变量真正存放的地方。

比如：

```java
static int count = 0;
```

这个 `count` 可以理解为在主内存里。

## 2. 工作内存

每个线程都有自己的“工作内存”。

线程操作共享变量时，不一定直接改主内存，而可能是：

1. 先从主内存读取到自己的工作内存
2. 在线程自己的工作内存里操作
3. 再刷新回主内存

所以线程之间通信，本质上是通过**主内存**完成的。

------

# 三、画成一句人话

你可以这样记：

**主内存是公共仓库，工作内存是每个线程自己的小本本。**

线程先把数据抄到自己本子上，改完以后再决定什么时候写回公共仓库。

问题就来了：

- 你改了自己的本子，别人可能不知道
- 你看的还是旧记录，不是最新值
- 多个人一起改，还可能互相覆盖

这就引出了三个核心问题。

------

# 四、原子性到底是什么

## 定义

一个操作要么全部完成，要么完全不做，中间不能被别的线程打断。

------

## 例子：`count++` 不是原子操作

```java
count++;
```

它并不是一步完成的，底层大致可以拆成：

1. 读 `count`
2. `count + 1`
3. 写回 `count`

假设两个线程同时做：

- 线程 A 读到 `count = 10`
- 线程 B 也读到 `count = 10`
- A 写回 11
- B 也写回 11

本来应该变成 12，结果却是 11。

这就是原子性被破坏了。

------

## 再看一个生活例子

两个人同时在纸上记库存：

- 库存原来是 100
- A 看到 100，减 1，写 99
- B 也看到 100，减 1，写 99

实际卖了两件，最后只少了一件。

这也是原子性问题。

------

# 五、可见性到底是什么

## 定义

一个线程修改了共享变量，另一个线程能否立刻看到最新值。

------

## 还是看 `flag`

```java
static boolean flag = false;
```

线程 A：

```java
while (!flag) {
}
```

线程 B：

```java
flag = true;
```

如果 A 一直用的是自己工作内存里的旧值 `false`，就算 B 已经改成 `true`，A 也可能不知道。

这就是可见性问题。

------

## 你可以这样理解

- 主内存里已经是新值了
- 但某个线程手里还拿着旧副本
- 它没及时同步，所以“看不见”

------

## 谁能解决可见性

后面你会学到：

- `volatile` 可以保证可见性
- `synchronized` 也能保证可见性
- `Lock` 也能保证可见性

但它们解决问题的方式不完全一样。

------

# 六、有序性到底是什么

## 定义

程序执行时，代码的实际执行顺序，未必完全等于你写的顺序。

为什么？

因为编译器和 CPU 可能会为了性能做优化，也就是：

**指令重排**

------

## 先说一句关键话

在**单线程**里，重排通常不会影响结果。
因为编译器会保证：

**最终执行效果和你写的代码逻辑一致。**

但在**多线程**里，别的线程可能看到一个“中间状态”，这就可能出问题。

------

## 举个简单例子

```java
int a = 1;
int b = 2;
```

你写的是先给 `a` 赋值，再给 `b` 赋值。
但实际底层为了优化，顺序可能调整。

单线程下你一般察觉不到。
但多线程下，如果另一个线程正在观察这些变量，就可能看到你意想不到的状态。

------

## 经典场景：对象创建不是绝对“看上去那么顺”

比如：

```java
instance = new Singleton();
```

这句话表面上一行，实际可能包含多个步骤：

1. 分配内存
2. 初始化对象
3. 把引用赋给 `instance`

如果发生重排，步骤 2 和 3 的顺序可能对别的线程看来不安全。
别的线程可能看到：

- `instance` 已经不是 `null`
- 但对象还没初始化完成

这就是有序性问题在实际开发里的经典坑。

------

# 七、这三个概念的关系

你千万别把它们混了。

## 原子性

强调的是：

**一个操作会不会被打断**

关键词：完整性

------

## 可见性

强调的是：

**一个线程改了，别的线程看不看得见**

关键词：最新值

------

## 有序性

强调的是：

**代码执行顺序是否符合预期**

关键词：顺序

# 九、JMM 为什么要允许这些问题存在？

你可能会想：

“那 Java 干嘛不强制所有线程每次都直接读主内存，按代码顺序执行，不就没问题了？”

因为那样性能会很差。

现代 CPU 为了快，会做很多优化：

- 寄存器缓存
- CPU 高速缓存
- 指令重排
- 编译优化

所以 JMM 的本质不是“完全禁止优化”，而是：

**在性能和线程安全之间做规则约束。**

也就是说：

- 可以优化
- 但要在规定条件下，保证多线程结果可控

# 第三课：volatile 到底是什么？它能解决什么，不能解决什么

这一课你要真正搞清 3 件事：

1. `volatile` 到底能做什么
2. `volatile` 不能做什么
3. 什么时候该用它，什么时候不能用它

------

# 一、先看最经典的场景

```java
public class Demo {
    static boolean flag = false;

    public static void main(String[] args) {
        new Thread(() -> {
            while (!flag) {
            }
            System.out.println("线程结束");
        }).start();

        new Thread(() -> {
            flag = true;
            System.out.println("flag 已修改");
        }).start();
    }
}
```

这个程序的问题是：

第二个线程已经把 `flag` 改成 `true` 了，
第一个线程却可能一直卡在 `while (!flag)` 里。

原因我们上一课讲过：

**可见性问题。**

线程 A 改了共享变量，线程 B 不一定马上看得到。

这时，把代码改成：

```java
public class Demo {
    static volatile boolean flag = false;

    public static void main(String[] args) {
        new Thread(() -> {
            while (!flag) {
            }
            System.out.println("线程结束");
        }).start();

        new Thread(() -> {
            flag = true;
            System.out.println("flag 已修改");
        }).start();
    }
}
```

这次通常就正常了。

------

# 二、volatile 到底是什么

你先记最实用的定义：

**volatile 是一个变量修饰符，用来告诉 JVM：这个变量是多个线程共享的，对它的读写要更“直接”和“及时”。**

它最核心的作用有两个：

- 保证可见性
- 保证一定程度的有序性

它**不保证原子性**。

这个第三点非常重要。

------

# 三、volatile 如何保证可见性

你可以先用“通俗版”理解：

普通共享变量，线程可能会把它的值缓存到自己的工作内存里。
而 `volatile` 变量，每次读取都更强调“去看最新值”，每次写入也更强调“立刻让其他线程知道”。

所以：

- 一个线程修改了 `volatile` 变量
- 其他线程随后读取时，更容易读到最新值

------

## 你可以先这样记

### 普通变量

像每个人记在自己的草稿纸上，未必同步。

### volatile 变量

更像每次都要看公告板，而且改完要立刻更新公告板。

这个比喻不严谨，但很适合入门。

------

# 四、volatile 能解决什么问题

## 1. 状态标记问题

这是 `volatile` 最经典的适用场景。

例如停止线程：

```java
public class Demo {
    static volatile boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            while (running) {
                // 执行任务
            }
            System.out.println("线程停止");
        });

        t.start();

        Thread.sleep(1000);
        running = false;
    }
}
```

这里 `running` 就很适合用 `volatile`。

因为这里不需要复合操作，只需要：

**一个线程改状态，另一个线程及时看到。**

------

## 2. 单次写、多次读的配置变量

比如：

- 开关
- 标志位
- 是否结束
- 是否刷新
- 是否加载完成

这类变量的特点是：

- 赋值动作比较简单
- 不涉及 `++`、`--`、判断再修改这种复合逻辑

这时 `volatile` 往往比较合适。

------

# 五、volatile 不能解决什么问题

这部分最关键。

## volatile 不能保证原子性

看代码：

```java
public class Demo {
    static volatile int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 10000; i++) {
                count++;
            }
        });

        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 10000; i++) {
                count++;
            }
        });

        t1.start();
        t2.start();

        t1.join();
        t2.join();

        System.out.println(count);
    }
}
```

很多初学者会以为：

“我都加 `volatile` 了，结果应该就是 20000 吧？”

其实不一定。

因为：

**`count++` 仍然不是原子操作。**

它还是三步：

1. 读
2. 加
3. 写

`volatile` 只能保证你读到的是较新的值，
但不能保证这三步执行过程中不被别的线程插进来。

所以多个线程同时 `count++`，照样会丢失更新。

------

## 一句话记住

**volatile 解决的是“看得见”，不是“改得完整”。**

这句话你一定要背住。

------

# 六、那 volatile 和 synchronized 的区别是什么

这是高频对比题。

## volatile

能保证：

- 可见性
- 一定程度的有序性

不能保证：

- 原子性

------

## synchronized

能保证：

- 原子性
- 可见性
- 有序性

因为 `synchronized` 本质上是同步互斥：

- 同一时刻只让一个线程进入临界区
- 退出同步块时会把修改刷新出去
- 进入同步块时会读取最新值

所以它能力更强，但一般也更重。

------

# 七、volatile 为什么还能保证有序性

这里说“有序性”，不是说完全禁止所有重排。

更准确地说：

**volatile 可以禁止和它相关的一些危险重排序。**

你先建立这个印象就够了。

------

## 例子：指令重排风险

比如：

```java
instance = new Singleton();
```

表面上是一句，底层可能是：

1. 分配对象内存
2. 初始化对象
3. 把引用赋值给 `instance`

如果发生重排，可能变成：

1. 分配内存
2. 把引用赋给 `instance`
3. 初始化对象

这样另一个线程看到 `instance != null` 时，
对象可能还没初始化完。

这就是多线程下有序性问题。

------

## volatile 的作用

如果把这个共享引用用 `volatile` 修饰，
它可以在一定程度上阻止这种危险重排。

这也是双重检查单例里常见的原因，后面会专门讲。

------

# 八、什么时候适合用 volatile

你可以记一个判断标准：

**一个变量的值，是否依赖于它当前的旧值？**

如果依赖，通常不能只靠 `volatile`。

------

## 适合用 volatile 的场景

### 场景 1：布尔开关

```java
volatile boolean running = true;
```

### 场景 2：状态通知

```java
volatile boolean initialized = false;
```

### 场景 3：一个线程写，多个线程读

比如配置刷新标志、任务结束标志。

------

## 不适合只用 volatile 的场景

### 场景 1：计数器

```java
count++;
```

### 场景 2：复合判断再修改

```java
if (count == 0) {
    count = 1;
}
```

### 场景 3：多个变量需要保持一致性

比如：

```java
a = 10;
b = 20;
```

如果你要求别的线程看到它们时必须同时一致，那单靠 `volatile` 不够。

------

# 九、最容易犯的误区

## 误区 1：给变量加了 volatile 就线程安全了

不对。

`volatile` 不是万能线程安全工具。
它只解决一部分问题。

------

## 误区 2：volatile 可以代替锁

大多数情况下不行。

只要涉及：

- 复合操作
- 临界区
- 多步共享状态修改

就往往还是要锁，或者原子类。

------

## 误区 3：volatile 会让程序绝对更快

也不能这么说。

它通常比加锁轻量，但也不是零成本。
而且用错了，程序虽然“快”，但结果是错的。

------

# 十、面试里最常见的一句回答

面试官问：

**volatile 有什么作用？**

你可以答：

`volatile` 用于修饰共享变量，主要作用是保证该变量在多线程之间的可见性，并且可以禁止与该变量相关的部分指令重排序，从而保证一定的有序性。但它不能保证复合操作的原子性，因此像 `count++` 这类操作即使使用 `volatile` 也仍然线程不安全。

这段回答已经很标准了。

# 第四课：`synchronized` 到底锁的是什么？对象锁、类锁、同步方法怎么理解

这一课非常关键。
很多人学 `synchronized` 时，表面会写，但脑子里一直糊涂：

- 到底锁的是代码，还是对象？
- 普通同步方法和静态同步方法有什么区别？
- 两个线程为什么有时互斥，有时又能同时执行？

这一课我们就把这些问题讲清楚。

------

# 一、先说结论：`synchronized` 锁的不是代码，锁的是对象

这是你最先要记住的一句话：

**`synchronized` 真正锁住的是某个对象的监视器（monitor）。**

你先别管 monitor 这个词有多底层，入门阶段你可以直接理解成：

**每个对象都可以当一把锁。**

所以 `synchronized` 不是说“这段代码天生带锁”，而是说：

**线程进入这段同步代码前，必须先拿到某个对象对应的锁。**

------

# 二、先看最基础的写法

## 写法 1：同步代码块

```java
public class Demo {
    private final Object lock = new Object();

    public void method() {
        synchronized (lock) {
            System.out.println("执行同步代码");
        }
    }
}
```

这里锁的是谁？

答案是：

**`lock` 这个对象。**

也就是说：

- 线程 A 进入 `synchronized(lock)`，拿到 `lock` 的锁
- 线程 B 也想进 `synchronized(lock)`，就得等 A 出来

------

## 重点

`synchronized(谁)`，锁的就是谁。

这个规则非常重要。

------

# 三、为什么要“锁对象”

因为多线程竞争的是共享资源。
Java 的设计思路是：

**把“互斥访问权”绑定到某个对象上。**

你可以把对象想成会议室钥匙：

- 谁拿到钥匙，谁能进会议室
- 其他人只能在外面等

所以同步的核心不是“代码长什么样”，而是：

**多个线程是不是在抢同一把锁。**

------

# 四、如果锁的不是同一个对象，会怎样

看代码：

```java
public class Demo {
    public void method() {
        synchronized (new Object()) {
            System.out.println(Thread.currentThread().getName() + " 执行");
        }
    }
}
```

这个写法有问题。

因为每次执行：

```java
new Object()
```

都会创建一个新对象。

也就是说每个线程拿到的都不是同一把锁，而是各拿各的锁。

结果就是：

**表面写了 `synchronized`，实际上起不到线程互斥效果。**

------

## 你要记住

想让多个线程互斥，必须满足：

**它们竞争的是同一把锁。**

------

# 五、实例方法上的 `synchronized` 锁的是什么

看代码：

```java
public class Demo {
    public synchronized void method() {
        System.out.println("同步实例方法");
    }
}
```

这个写法等价于：

```java
public void method() {
    synchronized (this) {
        System.out.println("同步实例方法");
    }
}
```

所以结论是：

## 普通 `synchronized` 方法锁的是：

**当前对象，也就是 `this`**

------

## 举例理解

```java
public class Demo {
    public synchronized void m1() {
        System.out.println("m1");
    }

    public synchronized void m2() {
        System.out.println("m2");
    }
}
```

如果：

```java
Demo d = new Demo();
```

两个线程同时调用：

- 线程 A：`d.m1()`
- 线程 B：`d.m2()`

它们会互斥。

因为：

- `m1()` 锁的是 `d`
- `m2()` 锁的也是 `d`

同一个对象，同一把锁，所以互斥。

------

# 六、如果是两个不同对象呢

```java
Demo d1 = new Demo();
Demo d2 = new Demo();
```

两个线程分别调用：

- 线程 A：`d1.m1()`
- 线程 B：`d2.m2()`

这时一般不会互斥。

因为：

- A 锁的是 `d1`
- B 锁的是 `d2`

不是同一把锁。

------

## 这里你要形成一个判断公式

是否互斥，不看方法名，主要看两件事：

### 1. 锁对象是不是同一个

### 2. 执行时间是不是重叠

只要锁对象不同，就可以并发执行。

------

# 七、静态 `synchronized` 方法锁的是什么

看代码：

```java
public class Demo {
    public static synchronized void method() {
        System.out.println("静态同步方法");
    }
}
```

它锁的不是 `this`。

因为静态方法不属于对象，而属于类。

它等价于：

```java
public class Demo {
    public static void method() {
        synchronized (Demo.class) {
            System.out.println("静态同步方法");
        }
    }
}
```

所以结论：

## 静态 `synchronized` 方法锁的是：

**当前类的 Class 对象**

也就是：

```java
Demo.class
```

------

# 八、对象锁和类锁的区别

这是高频重点。

## 对象锁

锁某个具体实例对象，比如：

- `this`
- `lock`
- `d1`
- `d2`

不同对象，有不同锁。

------

## 类锁

锁的是类模板本身，比如：

```java
Demo.class
```

无论你 new 多少个对象，`Demo.class` 在 JVM 里通常只有一份。

所以类锁是整个类级别的锁。

------

# 九、对象锁和类锁会互斥吗

通常：

**不会互斥。**

因为它们不是同一把锁。

看代码：

```java
public class Demo {
    public synchronized void m1() {
        System.out.println("实例同步方法");
    }

    public static synchronized void m2() {
        System.out.println("静态同步方法");
    }
}
```

- `m1()` 锁的是 `this`
- `m2()` 锁的是 `Demo.class`

这两把锁不同。

所以：

- 一个线程调实例同步方法
- 另一个线程调静态同步方法

它们一般可以同时执行。

------

# 十、用表格帮你彻底分清

| 写法                                  | 锁对象         |
| ------------------------------------- | -------------- |
| `synchronized(obj)`                   | `obj`          |
| `public synchronized void m()`        | `this`         |
| `public static synchronized void m()` | `当前类.class` |

这个表你最好直接记住。

# 十一、再看几个经典判断题

## 情况 1：两个线程调用同一个对象的两个同步实例方法

```java
Demo d = new Demo();
```

- 线程 A 调 `d.m1()`
- 线程 B 调 `d.m2()`

会互斥吗？

**会。**

因为都锁 `d`，也就是 `this`。

------

## 情况 2：两个线程调用不同对象的同步实例方法

```java
Demo d1 = new Demo();
Demo d2 = new Demo();
```

- A 调 `d1.m1()`
- B 调 `d2.m2()`

会互斥吗？

**一般不会。**

因为锁对象不同。

------

## 情况 3：两个线程调用同一个类的静态同步方法

```java
Demo.m1();
Demo.m2();
```

如果这两个方法都是 `static synchronized`，会互斥吗？

**会。**

因为它们都锁 `Demo.class`。

------

## 情况 4：一个线程调实例同步方法，一个线程调静态同步方法

会互斥吗？

**一般不会。**

因为：

- 一个锁 `this`
- 一个锁 `Demo.class`

不是同一把锁。

# 十二、为什么 `synchronized(this)` 要慎用

看代码：

```java
public class Demo {
    public void method() {
        synchronized (this) {
            // 业务代码
        }
    }
}
```

这本身没错。
但问题在于：`this` 有时候暴露给外部了。

外部代码也可能写：

```java
synchronized(demo) {
    // ...
}
```

这样别人也能抢你的锁，容易造成耦合和意外阻塞。

所以在实际开发里，更常见的写法是：

```java
private final Object lock = new Object();

synchronized (lock) {
    // ...
}
```

这样锁更私有、更可控。

------

# 十三、`synchronized` 能保证什么

前面我们讲过三大问题：

- 原子性
- 可见性
- 有序性

`synchronized` 都能保证。

## 1. 原子性

同一时刻只允许一个线程进入同步代码块。

## 2. 可见性

线程退出同步块时，对共享变量的修改会刷新；别的线程进入同步块时可以看到最新值。

## 3. 有序性

同步代码块内部在语义上是有序的，能约束并发访问顺序。

------

# 十四、一个经典错误：锁范围不对

看代码：

```java
public class Demo {
    private int count = 0;

    public void add() {
        synchronized (this) {
            count++;
        }
    }
}
```

如果多个线程操作的是**同一个对象**，这个写法没问题。

但如果你这样用：

```java
new Demo().add();
new Demo().add();
```

那其实每次都是新对象，锁就不是同一个了。

所以你会发现：

**线程安全不只取决于你写没写 `synchronized`，还取决于锁对象是不是共享的。**

这句话很重要。

------

# 十五、面试里怎么答“`synchronized` 锁的是什么”

你可以这样答：

`synchronized` 锁的不是代码，而是某个对象的监视器。对于同步代码块，锁的是括号里指定的对象；对于普通同步方法，锁的是当前实例对象 `this`；对于静态同步方法，锁的是当前类对应的 `Class` 对象。线程之间是否互斥，关键要看它们竞争的是否是同一把锁。

这段回答已经很标准了。

------

# 十六、你现在必须会的一个判断口诀

**先看是不是同一把锁，再看是不是同时执行。**

只要不是同一把锁，就 usually 不互斥。
哪怕方法上都写了 `synchronized`，也不一定互斥。

# 第五课：`synchronized` 为什么能保证线程安全？它的底层执行逻辑怎么理解

前一课你已经知道了：

- `synchronized` 锁的不是代码，而是对象
- 同步实例方法锁的是 `this`
- 静态同步方法锁的是 `Class` 对象

这一课我们再进一步：

**为什么一个关键字加上去，线程就安全了？**

核心答案就三个字：

**互斥 + 同步**

也就是：

- **互斥**：同一时刻只让一个线程进来
- **同步**：线程之间能看到彼此最新修改

这两个合起来，`synchronized` 才能真正保证线程安全。

------

# 一、先从最直观的角度理解

看代码：

```java
public class Demo {
    private int count = 0;

    public synchronized void add() {
        count++;
    }
}
```

为什么这里比不加锁安全？

因为当多个线程同时调用 `add()` 时：

- 线程 A 进来后，先拿到这把锁
- 在 A 还没执行完之前，线程 B 不能进来
- 所以 `count++` 虽然本身不是原子操作
- 但因为整个方法被“包起来”了，同一时刻只有一个线程执行它

于是：

**本来不原子的操作，被互斥保护后，整体看起来就变成“安全的临界区操作”了。**

------

# 二、什么叫临界区

这是并发里一个很常见的词。

**临界区**就是：

**访问共享资源的那段代码。**

比如：

```java
count++;
```

因为 `count` 是共享变量，所以这里就是临界区。

如果多个线程同时进入临界区，就可能出问题。
所以要加锁保护。

你可以把 `synchronized` 理解为：

**给临界区门口安排了保安，一次只放一个人进去。**

------

# 三、`synchronized` 保证线程安全的第一层原因：互斥

这是最核心的一层。

## 互斥是什么意思

同一时刻，只允许一个线程持有同一把锁。

比如：

```java
synchronized (lock) {
    // 临界区
}
```

执行逻辑可以这样理解：

1. 线程先尝试获取 `lock` 这把锁
2. 拿到锁，进入同步代码块
3. 没拿到锁，就在外面等
4. 执行完后释放锁
5. 其他线程再来竞争

所以 `synchronized` 最本质的能力就是：

**串行化对共享资源的访问。**

------

# 四、为什么互斥能解决原子性问题

你前面学过：

```java
count++;
```

不是原子操作，因为它分三步：

1. 读
2. 加
3. 写

如果没有锁，两个线程可能交错执行，导致丢失更新。

但如果把它放进同步块：

```java
synchronized (this) {
    count++;
}
```

那就变成：

- A 先完整执行完读、加、写
- A 释放锁
- B 再执行自己的读、加、写

虽然 `count++` 本身底层还是三步，
但因为整个过程不会被别的线程插进来，所以效果上就安全了。

所以：

**`synchronized` 不是让 `count++` 变成单条指令，而是让别的线程没机会在中间捣乱。**

这句话很重要。

------

# 五、`synchronized` 保证线程安全的第二层原因：可见性

`synchronized` 不只是“挡别人”，它还解决了“别人看不见”的问题。

## 为什么会有可见性问题

线程执行时，可能会把共享变量缓存到自己的工作内存里。
如果线程 A 改了值，线程 B 不一定立刻看得到。

------

## `synchronized` 怎么解决

你先记结论：

- **线程释放锁之前，会把对共享变量的修改刷新出去**
- **线程获取锁之后，会重新读取共享变量的最新值**

所以：

- A 在同步块里改了 `count`
- A 退出同步块
- B 之后进入同一把锁保护的同步块时
- B 能看到 A 改后的新值

这就是为什么 `synchronized` 也能保证可见性。

------

# 六、`synchronized` 保证线程安全的第三层原因：有序性

你前面还学过有序性，也就是指令重排问题。

`synchronized` 也能保证一定的有序性。

你现在先不用背底层指令规则，只要记住：

**在同步块内部，程序的执行结果对拿到同一把锁的线程来说是有序且可感知的。**

换句话说：

- 同步块前后的执行关系会受到约束
- 不能随便把同步相关的操作乱重排

所以 `synchronized` 也属于 JMM 下的重要同步手段。

------

# 七、所以 `synchronized` 为什么安全，可以浓缩成一句话

**因为它通过同一把锁实现互斥访问，并通过锁的获取与释放建立线程之间的内存可见性和执行顺序约束。**

这句话已经很接近标准答案了。

------

# 八、底层执行时，你可以怎么理解

先讲一个不死板、但很实用的理解模型。

## 你可以把每个对象想成带一把门锁

当线程执行：

```java
synchronized (obj) {
    // ...
}
```

就像在做这件事：

- 到 `obj` 门口申请钥匙
- 拿到了才能进
- 出来时归还钥匙

如果别的线程也想进这个 `obj` 对应的同步区：

- 没钥匙就只能等

------

## 这把“钥匙”在 JVM 里对应什么

对应对象关联的 **monitor（监视器）**。

入门阶段你记成：

**每个对象都可以关联一个监视器锁。**

`synchronized` 实际上就是围绕这个 monitor 做获取和释放。

------

# 九、同步代码块和同步方法在字节码层面有点不同

这里我只给你建立印象，不展开得太底层。

## 同步代码块

通常会对应一对操作：

- 进入监视器
- 退出监视器

你可以理解成：

- 进门上锁
- 出门解锁

------

## 同步方法

方法本身会带一个“这是同步方法”的标记，JVM 调用这个方法时会自动做同步控制。

你现在不用死记字节码名字，先知道：

**不管写法看起来是同步代码块还是同步方法，本质都是基于 monitor 做互斥。**

------

# 十、为什么说 `synchronized` 是“自动释放锁”的

看对比：

## `Lock` 的写法

```java
lock.lock();
try {
    // 业务代码
} finally {
    lock.unlock();
}
```

必须手动释放。

------

## `synchronized` 的写法

```java
synchronized (lock) {
    // 业务代码
}
```

代码块执行完，锁会自动释放。
哪怕中间抛异常，一般也会自动退出并释放。

这也是 `synchronized` 很适合入门和很多简单场景的原因：

**不容易因为忘记解锁而出问题。**

------

# 十一、`synchronized` 线程安全的边界在哪

这点很重要。

不是你只要写了 `synchronized` 就一定万无一失。

它成立有前提：

## 1. 必须锁的是同一把锁

比如：

```java
synchronized (this)
```

只有多个线程操作的是同一个对象实例，才有互斥效果。

------

## 2. 共享资源必须被这把锁完整保护

比如：

```java
public void add() {
    synchronized (this) {
        count++;
    }
}
```

如果别处还有代码不加锁直接改 `count`，那仍然不安全。

所以并发里有个重要原则：

**同一个共享资源，要么都不用锁，要么统一用同一把锁保护。**

乱用不同锁，等于没锁好。

------

# 十二、一个常见误区：锁住方法就一定锁住数据了吗

不一定。

看代码：

```java
public class Demo {
    private int count = 0;

    public synchronized void add() {
        count++;
    }

    public void sub() {
        count--;
    }
}
```

这里 `add()` 加锁了，但 `sub()` 没加锁。
如果多个线程同时调用，`count` 还是可能出问题。

所以：

**真正被保护的不是“某个方法名”，而是“对共享变量的所有访问路径”。**

这句话你最好记住。

------

# 十三、再讲一个容易懂的生活比喻

假设一个保险柜里放着钱，很多人都要改余额。

如果没有规则：

- A 改一半
- B 插进来又改
- 数据就乱了

现在规定：

- 谁拿到保险柜钥匙，谁才能开柜子操作
- 操作完必须关好再把钥匙还回来
- 下一个人再进去

这样同一时刻只有一个人改余额，数据就不乱了。

这就是 `synchronized` 的互斥思想。

再加上：

- 每次开柜前看最新余额
- 关柜后把新余额保存好

这就是可见性。

所以 `synchronized` 的完整能力就是：

**独占访问 + 数据同步**

------

# 十四、面试里怎么答“`synchronized` 为什么能保证线程安全”

你可以这样答：

`synchronized` 之所以能够保证线程安全，是因为它基于对象监视器实现互斥访问。同一时刻只有一个线程能持有同一把锁并进入同步代码，从而保证临界区操作的原子性。同时，线程在释放锁时会将对共享变量的修改刷新到主内存，线程在获取锁时会重新读取最新值，因此它还能保证可见性。此外，`synchronized` 还能够对同步区域内外的执行顺序形成约束，从而保证一定的有序性。

这段回答已经比较标准了。

------

# 十五、你现在最该掌握的图景

以后你看到：

```java
synchronized (obj) {
    // 操作共享资源
}
```

脑子里就要自动翻译成：

1. 先抢 `obj` 这把锁
2. 抢到后独占进入临界区
3. 执行期间别人不能进
4. 退出时释放锁并同步修改结果

只要你脑子里有这个过程，后面很多题都会顺。

# 十六、这一课的核心结论

你先记这 5 句：

## 1

**`synchronized` 保证线程安全，靠的是互斥 + 可见性 + 有序性。**

## 2

**互斥让同一时刻只有一个线程进入临界区。**

## 3

**释放锁会刷新修改，获取锁会读取新值，所以有可见性。**

## 4

**它本质基于对象的 monitor。**

## 5

**要想真正安全，必须用同一把锁保护同一份共享资源。**

# 第六课：`synchronized` 和 `volatile` 到底有什么区别？怎么选？

这节课非常重要。
因为前面你已经分别学了：

- `volatile`
- `synchronized`

但很多人学到这里会开始乱：

- 都能保证可见性，那它们是不是差不多？
- 为什么有了 `volatile` 还要 `synchronized`？
- 什么时候该用哪个？

这节课我们就把它们彻底分开。

------

# 一、先给结论

你先记一句最核心的话：

**`volatile` 是“变量级别”的可见性工具，`synchronized` 是“代码块级别”的同步互斥工具。**

再说得更直白一点：

- `volatile` 主要解决：**一个线程改了值，别的线程要马上看见**
- `synchronized` 主要解决：**多个线程同时操作共享资源时，不能乱来**

所以它们不是谁替代谁的关系，而是：

**解决的问题层次不同。**

------

# 二、先从共同点开始

## 它们的共同点

`volatile` 和 `synchronized` 都可以保证：

- **可见性**
- **一定的有序性**

也就是说：

- 一个线程修改了共享变量
- 另一个线程后续有机会看到新值

这一点它们都有。

------

# 三、核心区别：原子性

真正把它们拉开差距的，是这点：

## `volatile` 不能保证原子性

## `synchronized` 可以保证原子性

这是最重要的区别。

------

# 四、先看 `volatile` 的能力边界

```java
volatile int count = 0;
count++;
```

这安全吗？

**不安全。**

因为 `count++` 不是原子操作。

它还是会经历：

1. 读 `count`
2. `+1`
3. 写回去

`volatile` 只能保证你读到的是相对最新的值，
但不能保证这三步不被别的线程打断。

所以多个线程一起 `count++`，还是会丢失更新。

------

# 五、再看 `synchronized` 为什么可以

```java
synchronized (this) {
    count++;
}
```

这里虽然 `count++` 本身还是三步，
但是由于整个代码块被锁住了：

- 同一时刻只有一个线程能进来
- 别的线程必须等它执行完

所以不会出现两个线程同时改 `count` 的情况。

因此：

**`synchronized` 是通过互斥，把非原子操作保护成线程安全操作。**

------

# 六、最直白的对比

你可以这样理解：

## `volatile`

像公告板。

- 你改了内容，别人能尽快看到
- 但两个人同时改公告板，内容还是可能互相覆盖

------

## `synchronized`

像会议室加锁。

- 一次只允许一个人进去操作
- 操作完再出来
- 所以不会同时乱改

这个比喻很适合前期建立直觉。

------

# 七、它们分别适合什么场景

## `volatile` 适合的场景

特点是：

- 变量赋值很简单
- 不涉及复合操作
- 更像“通知”或“开关”

比如：

```java
volatile boolean running = true;
```

一个线程：

```java
while (running) {
    // 工作
}
```

另一个线程：

```java
running = false;
```

这里非常适合 `volatile`。

因为只需要：

**改了之后，别的线程能及时看到。**

------

## `synchronized` 适合的场景

特点是：

- 涉及多个线程同时修改共享状态
- 涉及复合操作
- 涉及临界区逻辑

比如：

```java
public synchronized void sell() {
    if (stock > 0) {
        stock--;
    }
}
```

这里就不能只靠 `volatile`。

因为这不是单纯“看见新值”的问题，
而是：

- 判断
- 再修改

这是一个复合操作，需要整体保护。

------

# 八、判断标准特别重要

你可以用这个问题快速判断：

**这个共享变量的操作，是否依赖它当前的旧值？**

如果依赖，通常 `volatile` 不够。

------

## 例子 1

```java
running = false;
```

依赖旧值吗？

**不依赖。**

这类通常可以用 `volatile`。

------

## 例子 2

```java
count++;
```

依赖旧值吗？

**依赖。**

因为必须先读旧值，再加 1。
这类通常不能只用 `volatile`。

------

## 例子 3

```java
if (count == 0) {
    count = 1;
}
```

依赖旧值吗？

**依赖。**

因为先判断再赋值，这是复合逻辑。
只用 `volatile` 不安全。

------

# 九、它们在使用粒度上也不同

## `volatile` 修饰的是变量

```java
volatile boolean flag;
```

它作用在某个字段上。

------

## `synchronized` 修饰的是一段同步访问逻辑

```java
synchronized (lock) {
    // 一段临界区代码
}
```

或者：

```java
public synchronized void method() {}
```

它保护的是一整段共享资源操作过程。

所以你可以记：

- `volatile` 管“一个值”
- `synchronized` 管“一段操作”

------

# 十、性能上怎么理解

很多人会问：

是不是 `volatile` 一定比 `synchronized` 快？

不能绝对这么说，但通常可以这样理解：

## 一般情况下

- `volatile` 比较轻量
- `synchronized` 成本更高一些，因为涉及互斥竞争

但注意：

**轻量不等于更适合。**

如果你本来就需要原子性和临界区保护，
你为了“快”硬用 `volatile`，那得到的只是错误结果。

所以并发里第一原则不是快，而是：

**先正确，再谈性能。**

------

# 十一、一个高频误区

## 误区：

“只要变量加上 `volatile`，这个变量就是线程安全的。”

这是错的。

更准确地说：

**`volatile` 修饰的变量，只是在读写这个变量本身时具备可见性保证；如果涉及复合操作，仍然不安全。**

这个表达很标准。

------

# 十二、最常见面试题：`volatile` 和 `synchronized` 的区别

你可以这样答：

`volatile` 和 `synchronized` 都可以保证多线程环境下的可见性，并且都能够在一定程度上限制指令重排序。但 `volatile` 只能保证对单个共享变量读写的可见性，不能保证复合操作的原子性，因此适合做状态标志、开关变量等场景。`synchronized` 则通过对象锁实现互斥访问，能够同时保证原子性、可见性和有序性，适合保护临界区和复合操作。

这段答案已经很像正式面试答案了。

| 作用范围 | 单个变量           | 代码块 / 方法    |
| 可见性   | 有                 | 有               |
| 原子性   | 没有               | 有               |

# 第七课：`Lock` 和 `synchronized` 有什么区别？为什么 JUC 里还要有 `ReentrantLock`

这一课开始，你就正式从“Java 并发基础”走到 “JUC 核心工具” 了。

因为前面你已经学会了：

- `volatile`
- `synchronized`

这时候很多人会问：

**既然 `synchronized` 都能加锁了，JUC 为什么还要提供 `Lock`？**

答案是：

**因为 `synchronized` 够简单，但不够灵活；`Lock` 更强大、更可控。**

------

# 一、先给结论

你先记住这句话：

**`synchronized` 是 Java 关键字，`Lock` 是 JUC 提供的锁接口。**

也就是说：

- `synchronized` 是语言层面的能力
- `Lock` 是类库层面的能力

而 JUC 里最常用的实现类就是：

**`ReentrantLock`**

------

# 二、先看最基本写法

## `synchronized` 写法

```java
public synchronized void method() {
    System.out.println("业务代码");
}
```

或者：

```java
synchronized (lock) {
    System.out.println("业务代码");
}
```

------

## `Lock` 写法

```java
Lock lock = new ReentrantLock();

lock.lock();
try {
    System.out.println("业务代码");
} finally {
    lock.unlock();
}
```

你一眼就能看出区别：

- `synchronized` 更简洁
- `Lock` 更显式

也就是说，`Lock` 需要你自己写：

- 加锁
- 解锁

------

# 三、它们的共同点

先别急着看区别，先看共同点。

`Lock` 和 `synchronized` 本质上都能做到：

- 保证临界区互斥
- 保证线程安全
- 解决共享资源并发访问问题

比如：

```java
count++;
```

本来不是线程安全的。

但不管你用：

- `synchronized`
- `ReentrantLock`

只要正确保护临界区，都能让它安全。

------

# 四、第一大区别：使用方式不同

## `synchronized`

是隐式加锁、隐式释放锁。

代码执行完，同步块结束，锁自动释放。
即使中间抛异常，通常也会自动释放。

这很省心。

------

## `Lock`

是显式加锁、显式释放锁。

你必须手动：

```java
lock.lock();
```

再手动：

```java
lock.unlock();
```

所以一定要写在 `finally` 里：

```java
lock.lock();
try {
    // 业务代码
} finally {
    lock.unlock();
}
```

否则一旦忘记解锁，别人就永远进不来了。

------

# 五、第二大区别：`Lock` 更灵活

这才是重点。

`synchronized` 虽然好用，但功能比较固定。
而 `Lock` 提供了更多高级能力。

最重要的几个你先记住：

- 可中断获取锁
- 尝试获取锁
- 超时获取锁
- 公平锁
- 多条件队列

这些都是 `synchronized` 很难直接做到的。

------

# 六、可中断获取锁

先说一个很实用的能力：

## `synchronized`

线程在等待锁时，比较被动。

一旦卡在那等锁，不容易灵活处理中断等待逻辑。

------

## `Lock`

可以这样写：

```java
lock.lockInterruptibly();
```

意思是：

**线程在等待锁的过程中，可以响应中断。**

这个能力在一些更复杂的并发控制里很有用。

比如：

- 任务取消
- 超时放弃
- 避免长时间死等

你现在先记住：
**`Lock` 获取锁更灵活。**

------

# 七、尝试获取锁

这是 `Lock` 特别常用的能力。

```java
if (lock.tryLock()) {
    try {
        System.out.println("拿到锁了");
    } finally {
        lock.unlock();
    }
} else {
    System.out.println("没拿到锁，直接走别的逻辑");
}
```

这是什么意思？

就是：

- 能拿到锁就执行
- 拿不到锁就不等了，直接干别的

而 `synchronized` 是做不到这种“试一下拿锁，不行就算了”的风格的。

所以 `Lock` 特别适合：

- 不想一直阻塞等待
- 想做降级处理
- 想控制等待策略

------

# 八、超时获取锁

`Lock` 还能这样：

```java
if (lock.tryLock(3, TimeUnit.SECONDS)) {
    try {
        System.out.println("3 秒内拿到锁");
    } finally {
        lock.unlock();
    }
} else {
    System.out.println("3 秒内没拿到锁，放弃");
}
```

这个就更灵活了：

- 最多等 3 秒
- 还拿不到就放弃

`synchronized` 做不到这种超时控制。

------

# 九、公平锁和非公平锁

这是 `ReentrantLock` 的一个重要特性。

## 非公平锁

默认是非公平的。

意思是：

**后来的线程有机会插队抢锁。**

优点：

- 吞吐量通常更高
- 效率更好

缺点：

- 某些线程可能等得比较久

------

## 公平锁

可以这样创建：

```java
Lock lock = new ReentrantLock(true);
```

`true` 表示公平锁。

公平锁的意思是：

**尽量按等待顺序来拿锁，先来先得。**

优点：

- 更公平

缺点：

- 一般性能会差一点

------

## `synchronized`

你不能直接指定它是公平锁还是非公平锁。

这也是 `Lock` 更灵活的地方。

------

# 十、多条件等待队列

这个点是 JUC 非常核心的优势之一。

你前面学过 `wait()` / `notify()` 的话，会知道：

`synchronized` 配合的是：

- `wait()`
- `notify()`
- `notifyAll()`

这种方式可以做线程通信，但不够灵活。

------

## `Lock` 可以配合 `Condition`

```java
Lock lock = new ReentrantLock();
Condition condition = lock.newCondition();
```

然后：

- `condition.await()`
- `condition.signal()`
- `condition.signalAll()`

最大的优势是：

**一个锁可以创建多个 `Condition`，也就是多个等待队列。**

这比 `synchronized` 那种单一等待集合更灵活得多。

后面你学生产者消费者模型时，会明显感觉到这个优势。

------

# 十一、那为什么还要用 `synchronized`

讲到这你可能会觉得：

“那 `Lock` 这么强，干脆全用它不就好了？”

也不是。

因为 `synchronized` 也有很大优点。

------

## `synchronized` 的优点

### 1. 写法简单

语法更短，更不容易写错。

### 2. 自动释放锁

不容易忘记 `unlock()`。

### 3. 适合简单同步场景

很多普通临界区保护，用它就够了。

### 4. JVM 层面深度优化

现代 Java 里，`synchronized` 性能已经比早年好很多，不是以前那种“很重”的刻板印象了。

所以不是说 `Lock` 一定更好，而是：

**复杂场景优先考虑 `Lock`，简单场景 `synchronized` 非常合适。**

------

# 十二、`ReentrantLock` 里的“可重入”是什么意思

这个词你必须懂。

## 可重入

意思是：

**同一个线程已经拿到这把锁后，还可以再次进入这把锁保护的代码，而不会把自己锁死。**

------

## 举例

```java
public class Demo {
    private final Lock lock = new ReentrantLock();

    public void m1() {
        lock.lock();
        try {
            System.out.println("m1");
            m2();
        } finally {
            lock.unlock();
        }
    }

    public void m2() {
        lock.lock();
        try {
            System.out.println("m2");
        } finally {
            lock.unlock();
        }
    }
}
```

这里：

- `m1()` 已经拿到锁
- 调用 `m2()` 时，又再次拿这把锁
- 因为它是可重入锁，所以不会死锁

`synchronized` 其实也是可重入的。

所以“可重入”不是 `ReentrantLock` 独有，而是它和 `synchronized` 都有的特性。

# 一、先看最标准的基本写法

这是你必须先背熟的模板：

```java
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class Demo {
    private final Lock lock = new ReentrantLock();
    private int count = 0;

    public void add() {
        lock.lock();
        try {
            count++;
            System.out.println(Thread.currentThread().getName() + " -> " + count);
        } finally {
            lock.unlock();
        }
    }
}
```

这个模板最核心的结构就是：

```java
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}
```

你一定要养成这个习惯。

因为 `ReentrantLock` 是**手动加锁、手动释放锁**，如果你忘了 `unlock()`，问题会很严重。

------

# 二、为什么一定要写在 `finally` 里

看这个错误写法：

```java
lock.lock();
count++;
lock.unlock();
```

表面没问题，但如果 `count++` 中间或者后面的业务代码抛异常了，就可能执行不到 `unlock()`。

结果就是：

**这把锁一直不释放，其他线程就永远拿不到。**

所以正确写法必须是：

```java
lock.lock();
try {
    // 业务代码
} finally {
    lock.unlock();
}
```

这是 `ReentrantLock` 第一铁律。

------

# 三、`ReentrantLock` 到底是什么意思

这个名字你拆开看：

- `entrant`：进入
- `re`：再次

合起来就是：

**可以重复进入的锁**

也就是：

**同一个线程已经拿到这把锁后，还可以再次获取这把锁。**

这就叫可重入。

------

# 四、可重入到底有什么用

看例子：

```java
import java.util.concurrent.locks.ReentrantLock;

public class Demo {
    private final ReentrantLock lock = new ReentrantLock();

    public void m1() {
        lock.lock();
        try {
            System.out.println("进入 m1");
            m2();
        } finally {
            lock.unlock();
        }
    }

    public void m2() {
        lock.lock();
        try {
            System.out.println("进入 m2");
        } finally {
            lock.unlock();
        }
    }
}
```

这里：

- 线程先进入 `m1()`，拿到锁
- `m1()` 里面又调用 `m2()`
- `m2()` 再次获取同一把锁

如果这把锁不可重入，那线程会把自己卡死。
但 `ReentrantLock` 允许同一个线程重复拿锁，所以不会死锁。

------

## 这里要特别注意

拿了几次锁，就要解几次锁。

比如：

- `m1()` 里 `lock()` 一次
- `m2()` 里又 `lock()` 一次

那最终也必须：

- `m2()` `unlock()` 一次
- `m1()` 再 `unlock()` 一次

否则锁不会真正释放。

------

# 五、`ReentrantLock` 的内部你可以先这样理解

它会记录两件事：

## 1. 当前持有锁的是哪个线程

## 2. 这个线程重入了多少次

所以同一个线程反复 `lock()` 没问题，
只是计数会加 1。

每次 `unlock()`，计数减 1。
只有减到 0，锁才真正释放给别的线程。

这个理解就够你现阶段用了。

------

# 六、公平锁和非公平锁是什么

这是 `ReentrantLock` 非常重要的特性。

先看默认写法：

```java
Lock lock = new ReentrantLock();
```

默认是：

**非公平锁**

------

## 非公平锁是什么意思

不是严格按排队顺序拿锁。

也就是说：

- 有些线程已经在等了
- 新来的线程也可能直接插队抢到锁

这就叫非公平。

------

## 为什么默认非公平

因为通常这样性能更好，吞吐量更高。

虽然看起来“不公平”，但效率往往更高。

------

# 七、公平锁怎么创建

```java
Lock lock = new ReentrantLock(true);
```

这里 `true` 表示：

**公平锁**

意思是：

**尽量按照线程等待的先后顺序来分配锁。**

谁先等，谁先拿。

------

# 八、公平锁和非公平锁怎么理解

你可以用食堂打饭来理解。

## 非公平锁

窗口刚空出来，后面刚跑来的一个人可能直接抢到前面。

优点：

- 更快
- 整体效率通常更高

缺点：

- 先来的人可能等更久

------

## 公平锁

严格按排队顺序来。

优点：

- 更公平
- 不容易让某些线程长期饿着

缺点：

- 一般性能差一点

------

# 九、该怎么选公平锁还是非公平锁

大多数业务场景下：

**默认非公平锁就可以。**

因为它通常吞吐量更好。

只有在你特别强调：

- 先来先服务
- 避免线程长期饥饿
- 调度公平性很重要

这种情况下，才考虑公平锁。

------

# 十、`tryLock()` 是什么

这是 `ReentrantLock` 很实用的能力，也是 `synchronized` 做不到的。

看代码：

```java
import java.util.concurrent.locks.ReentrantLock;

public class Demo {
    private final ReentrantLock lock = new ReentrantLock();

    public void test() {
        if (lock.tryLock()) {
            try {
                System.out.println("拿到锁，执行业务");
            } finally {
                lock.unlock();
            }
        } else {
            System.out.println("没拿到锁，直接返回");
        }
    }
}
```

意思是：

- 我试着拿一下锁
- 如果立刻拿到，就执行
- 如果拿不到，不等，直接走别的逻辑

------

# 十一、`tryLock()` 有什么用

这个方法特别适合：

## 1. 不想一直阻塞等待

比如请求很多时，不想线程全卡住。

## 2. 想做降级处理

拿不到锁就返回“系统繁忙”。

## 3. 避免某些死等场景

有时候宁可拿不到，也比一直傻等好。

------

# 十二、带超时的 `tryLock`

还可以这样写：

```java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Demo {
    private final ReentrantLock lock = new ReentrantLock();

    public void test() throws InterruptedException {
        if (lock.tryLock(3, TimeUnit.SECONDS)) {
            try {
                System.out.println("3 秒内拿到了锁");
            } finally {
                lock.unlock();
            }
        } else {
            System.out.println("3 秒内没拿到锁，放弃");
        }
    }
}
```

这表示：

- 最多等 3 秒
- 3 秒内拿到锁就执行
- 拿不到就放弃

这个在实际开发里比无限等待更灵活。

------

# 十三、`lockInterruptibly()` 是什么

这个也很关键。

```java
lock.lockInterruptibly();
```

意思是：

**线程在等待锁的过程中，可以响应中断。**

普通 `lock()` 的特点更像是：

- 要么拿到锁
- 要么一直等

而 `lockInterruptibly()` 允许你在等待过程中被打断。

------

## 它适合什么场景

比如：

- 任务取消
- 超时取消
- 不想让线程长时间卡死在锁等待上

你现在先记住这个结论就行：

**`lockInterruptibly()` 比 `lock()` 更适合需要取消等待的场景。**

------

# 十四、`ReentrantLock` 的几个常用方法总结

你可以先记这几个：

## 1. `lock()`

普通获取锁。拿不到就等。

## 2. `unlock()`

释放锁。

## 3. `tryLock()`

试着拿锁，拿不到立即返回 `false`。

## 4. `tryLock(time, unit)`

在指定时间内尝试拿锁。

## 5. `lockInterruptibly()`

可中断地获取锁。

------

# 十五、最常见错误 1：拿到锁后没有释放

错误示例：

```java
lock.lock();
if (count > 0) {
    return;
}
lock.unlock();
```

这里如果 `count > 0` 直接 `return`，那锁就没释放。

所以一定要写成：

```java
lock.lock();
try {
    if (count > 0) {
        return;
    }
} finally {
    lock.unlock();
}
```

------

# 十六、最常见错误 2：没有拿到锁却去解锁

比如：

```java
if (lock.tryLock()) {
    // do something
}
lock.unlock();
```

这就可能有问题。

因为如果 `tryLock()` 返回 `false`，说明根本没拿到锁，
你再 `unlock()` 就会抛异常。

正确写法是：

```java
if (lock.tryLock()) {
    try {
        // do something
    } finally {
        lock.unlock();
    }
}
```

------

# 十七、最常见错误 3：把 `ReentrantLock` 当成普通变量乱 new

比如：

```java
public void add() {
    ReentrantLock lock = new ReentrantLock();
    lock.lock();
    try {
        count++;
    } finally {
        lock.unlock();
    }
}
```

这其实没法真正实现线程互斥。

因为每次方法调用都会创建一把新锁，
线程之间根本不是竞争同一把锁。

正确做法是把锁定义成共享成员变量：

```java
private final ReentrantLock lock = new ReentrantLock();
```

这一点和 `synchronized(new Object())` 的坑很像。

------

# 十八、`ReentrantLock` 适合什么场景

相比 `synchronized`，它特别适合这些情况：

- 需要 `tryLock`
- 需要超时拿锁
- 需要响应中断
- 需要公平锁
- 后面要配合 `Condition` 做复杂线程通信

如果只是简单保护一小段临界区，`synchronized` 往往已经够用了。

# 十九、标准面试回答怎么说

如果面试官问：

**你说说 `ReentrantLock` 的特点。**

你可以这样答：

`ReentrantLock` 是 JUC 中 `Lock` 接口的常见实现类，它是一种可重入独占锁。可重入表示同一个线程在持有锁的情况下可以重复获取该锁，内部会记录重入次数。相比 `synchronized`，`ReentrantLock` 提供了更灵活的能力，例如支持公平锁和非公平锁、`tryLock` 非阻塞尝试获取锁、可中断获取锁以及超时获取锁等，因此更适合复杂并发控制场景。不过它需要手动释放锁，通常必须在 `finally` 中调用 `unlock()`。

这段回答已经比较完整了。

# 第九课：`Condition` 是什么？为什么它比 `wait/notify` 更强

这一课非常关键。
因为到了这里，`ReentrantLock` 才真正开始展现它和 `synchronized` 拉开差距的地方。

你前面已经知道：

- `synchronized` 能做同步互斥
- `wait/notify` 能做线程等待和唤醒
- `ReentrantLock` 更灵活

那问题来了：

**既然 `wait/notify` 已经能线程通信了，为什么 JUC 还要搞一个 `Condition`？**

答案是：

**因为 `Condition` 能把线程等待/唤醒控制得更细、更清楚、更灵活。**

------

# 一、先说结论

你先记一句话：

**`Condition` 是配合 `Lock` 使用的条件队列，用来实现线程之间的等待与唤醒。**

最常见的搭配就是：

```java
ReentrantLock + Condition
```

它和下面这组东西的关系很像：

```java
synchronized + wait/notify
```

也就是说：

- `wait/notify` 是 `synchronized` 体系里的通信方式
- `Condition` 是 `Lock` 体系里的通信方式

------

# 二、先回顾一下 `wait/notify` 的问题

你先别急着看 `Condition` 多好，先看为什么需要它。

假设你以前用 `synchronized` 写线程通信，大概是这样：

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }

    // 满足条件，继续执行
}
```

唤醒时：

```java
synchronized (lock) {
    condition = true;
    lock.notifyAll();
}
```

这当然能用，但它有几个明显问题。

------

## 1. `wait/notify` 必须依赖对象监视器

也就是说必须写在：

```java
synchronized (lock)
```

内部。

否则会抛异常。

------

## 2. 一个对象基本上只有一套等待队列思维

你可以简单理解成：

**大家都在同一个等待室里等。**

如果有很多种不同条件的线程都在等，就会很乱。

例如：

- 一批线程在等“队列不为空”
- 另一批线程在等“队列不为满”

它们都在同一个对象的等待集合里，唤醒时不够精准。

------

## 3. `notify/notifyAll` 语义不够直观

尤其是复杂场景里：

- `notify()` 唤醒谁不太好控制
- `notifyAll()` 又可能把不该唤醒的线程全唤醒，造成无效竞争

所以 `wait/notify` 能用，但在复杂线程协作场景下不够优雅。

------

# 三、`Condition` 到底是什么

`Condition` 你可以先理解成：

**锁上的一个“条件等待队列”。**

它让线程可以：

- 在某个条件不满足时等待
- 在条件满足时被精确唤醒

使用方式大概是这样：

```java
Lock lock = new ReentrantLock();
Condition condition = lock.newCondition();
```

这里：

- `lock` 是锁
- `condition` 是基于这把锁创建出来的条件对象

------

# 四、最基本用法先看一遍

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class Demo {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition condition = lock.newCondition();
    private boolean ready = false;

    public void awaitMethod() throws InterruptedException {
        lock.lock();
        try {
            while (!ready) {
                condition.await();
            }
            System.out.println("条件满足，继续执行");
        } finally {
            lock.unlock();
        }
    }

    public void signalMethod() {
        lock.lock();
        try {
            ready = true;
            condition.signal();
        } finally {
            lock.unlock();
        }
    }
}
```

你先看出它的结构：

## 等待

```java
condition.await();
```

## 唤醒

```java
condition.signal();
```

是不是很像：

- `wait()`
- `notify()`

没错，它们功能对应很接近。

------

# 五、`await()` 和 `wait()` 的对应关系

你可以这样记：

| `synchronized` 体系 | `Lock` 体系   |
| ------------------- | ------------- |
| `wait()`            | `await()`     |
| `notify()`          | `signal()`    |
| `notifyAll()`       | `signalAll()` |

这个对照表很重要。

------

# 六、`await()` 做了什么

当线程执行：

```java
condition.await();
```

它会做几件事：

## 1. 当前线程进入等待状态

## 2. 当前线程释放已经持有的锁

## 3. 等待别人唤醒

## 4. 被唤醒后重新竞争锁

## 5. 拿到锁后，从 `await()` 后面继续执行

这个流程和 `wait()` 的核心思想是一致的。

这里最重要的一点是：

**`await()` 不是拿着锁睡觉，而是会先释放锁。**

否则别的线程根本没机会进来修改条件并唤醒它。

------

# 七、`signal()` 做了什么

当线程执行：

```java
condition.signal();
```

它的意思是：

**唤醒一个在这个 `Condition` 上等待的线程。**

注意，是：

**在这个 `Condition` 上等待的线程**

不是所有等待线程。

这点很关键，后面你就会明白为什么它比 `wait/notify` 更强。

------

# 八、为什么 `Condition` 比 `wait/notify` 强

这里是本课核心。

最本质的原因是：

**一个 `Lock` 可以创建多个 `Condition`，也就是多个等待队列。**

比如：

```java
ReentrantLock lock = new ReentrantLock();
Condition notFull = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

你看到了吗？

同一把锁下，可以有：

- 一个等待“队列不满”的队列
- 一个等待“队列不空”的队列

这就比 `wait/notify` 灵活太多了。

------

# 九、举个最经典的例子：生产者消费者

假设有一个缓冲区。

## 生产者线程

如果缓冲区满了，就不能再生产，要等待“非满条件”。

## 消费者线程

如果缓冲区空了，就不能消费，要等待“非空条件”。

用 `Condition` 就可以很清晰地写成：

- 生产者等 `notFull`
- 消费者等 `notEmpty`

这样唤醒时也很精准：

- 生产完一个元素后，唤醒等“非空”的消费者
- 消费完一个元素后，唤醒等“非满”的生产者

这个就比一个对象上全靠 `notifyAll()` 乱喊一通要优雅很多。

------

# 十、看一个简化版生产者消费者

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class Buffer {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    private int count = 0;
    private final int capacity = 5;

    public void produce() throws InterruptedException {
        lock.lock();
        try {
            while (count == capacity) {
                notFull.await();
            }
            count++;
            System.out.println("生产一个，当前数量: " + count);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public void consume() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await();
            }
            count--;
            System.out.println("消费一个，当前数量: " + count);
            notFull.signal();
        } finally {
            lock.unlock();
        }
    }
}
```

这个例子你先不要急着背，先理解它的设计思路：

- 满了，生产者去 `notFull` 等
- 空了，消费者去 `notEmpty` 等
- 谁改变了状态，就精准叫醒对方

这就是 `Condition` 的强大之处。

------

# 十一、为什么等待要用 `while`，不要用 `if`

这是高频重点。

错误写法：

```java
if (!ready) {
    condition.await();
}
```

正确写法：

```java
while (!ready) {
    condition.await();
}
```

为什么？

因为线程被唤醒后，不代表条件一定真的满足。

可能有几种情况：

## 1. 虚假唤醒

线程可能在没有真正满足条件时被唤醒。

## 2. 被别的线程抢先改掉条件

比如多个线程都被唤醒了，先抢到锁的线程已经把资源拿走了，后面的线程再执行时条件又不满足了。

所以标准写法必须是：

**等待用 `while` 检查条件，不能偷懒用 `if`。**

这个规则和 `wait()` 完全一样。

------

# 十二、`Condition` 使用时的两个硬规则

## 规则 1：必须配合锁使用

也就是说，调用：

- `await()`
- `signal()`
- `signalAll()`

之前，必须先拿到对应的锁。

例如：

```java
lock.lock();
try {
    condition.await();
} finally {
    lock.unlock();
}
```

如果不在加锁状态下调用，会抛异常。

------

## 规则 2：一个 `Condition` 必须绑定创建它的那把锁

比如：

```java
Condition c = lock.newCondition();
```

那它就属于 `lock`。

你不能拿着别的锁去操作这个 `Condition`。

------

# 十三、`signal()` 和 `signalAll()` 怎么选

## `signal()`

唤醒一个等待线程。

适合：

- 你明确知道唤醒一个就够
- 条件队列划分已经比较清晰

## `signalAll()`

唤醒所有等待线程。

适合：

- 条件变化可能影响多个线程
- 或者你不确定唤醒一个是否足够

一般来说：

**如果等待队列分得足够清楚，`signal()` 的精确唤醒会更高效。**

------

# 十四、`Condition` 相比 `wait/notify` 的核心优势

你可以直接记这 4 点：

## 1. 可以有多个等待队列

这是最核心的优势。

## 2. 语义更清晰

`notFull`、`notEmpty` 这种命名可读性很好。

## 3. 唤醒更精准

可以唤醒特定条件队列里的线程。

## 4. 更适合复杂线程协作

尤其是生产者消费者、分组等待、复杂状态机这类场景。

------

# 十五、那 `Condition` 和 `wait/notify` 本质差别是什么

你可以这么理解：

**`wait/notify` 更像“一个房间里喊人”，而 `Condition` 更像“不同房间分别叫号”。**

这比喻非常贴切。

- `wait/notify`：大家都在一个大房间等
- `Condition`：可以分多个房间，各等各的条件

所以复杂协作时，`Condition` 明显更好用。

------

# 十六、面试里怎么答

如果面试官问：

**`Condition` 和 `wait/notify` 有什么区别？**

你可以这样答：

`Condition` 是 `Lock` 体系下用于线程等待和唤醒的条件对象，作用类似于 `synchronized` 中的 `wait/notify`。两者都可以实现线程通信，并且等待时都会释放锁、被唤醒后重新竞争锁。相比之下，`Condition` 的优势在于一个 `Lock` 可以创建多个 `Condition`，从而维护多个条件等待队列，实现更细粒度的等待与精准唤醒，因此在复杂线程协作场景下比 `wait/notify` 更灵活、更清晰。

这段回答已经很标准了。

# 十七、这节课你一定要记住的对应关系

你先把这个映射关系死死记住：

- `lock.lock()` 对应进入同步控制
- `condition.await()` 对应 `wait()`
- `condition.signal()` 对应 `notify()`
- `condition.signalAll()` 对应 `notifyAll()`

再记一句：

**`Condition` 最大优势：一把锁可以有多个条件队列。**

你判断下面哪个更适合用 `Condition`：

## 场景

有两个线程组：

- 一组在等“数据不为空”
- 一组在等“缓存不满”

这时更适合：

### B. `ReentrantLock` 配合两个 `Condition`

- `notEmpty`
